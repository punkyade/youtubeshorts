# 한국어 텍스트 전처리

TTS 품질의 절반은 전처리에서 갈린다. 엔진은 청크 단위로 억양을 만들기 때문에, 문장 중간에서 잘린 청크는 어색한 끝맺음 억양을 낳는다. 그래서 **자연스러운 경계에서 자르는 것**이 글자 수를 꽉 채우는 것보다 중요하다.

계약(시그니처, 보장 조건)은 `tts-architecture/references/contracts.md`의 `text/` 절을 따른다.

## Chunker 알고리즘

1. **단락 분리**: 빈 줄(`\n\s*\n`)로 먼저 나눈다. 단락 경계는 가장 강한 경계다.
2. **문장 분리**: 단락 안에서 아래 경계 뒤에서 나눈다.
   - 종결 부호: `. ! ? … 。 ！ ？` (연속 부호 `?!`, `...`는 하나로 취급)
   - 닫는 따옴표/괄호가 바로 뒤따르면 그것까지 포함해서 자른다: `"끝났다."` 다음에서 분리
   - 오탐 방지: 소수점(`3.14`), 약어(`Mr.`, `e.g.`, `vs.`), 숫자 목록(`1.`), URL·이메일 내부의 점에서는 자르지 않는다
3. **합치기**: 앞에서부터 문장을 `max_chars` 이하로 탐욕적으로 묶는다. 짧은 문장을 여러 번 요청하는 것보다 비용·속도·억양 모두 낫다.
4. **긴 문장 쪼개기** (한 문장이 `max_chars` 초과): 차례대로 시도한다.
   - 쉼표·세미콜론·콜론 → 연결 어미 뒤 공백(`-고 `, `-며 `, `-지만 `, `-는데 `, `-서 `) → 아무 공백
   - 공백조차 없이 `max_chars`를 넘으면 `TextTooLongError` (조용히 글자 단위로 자르지 않는다 — 단어를 깨뜨리면 엔진이 이상하게 읽는다)
5. **정리**: 각 청크 앞뒤 공백 제거, 빈 청크 제거.

## Normalizer 규칙

기본값은 공백 정리(연속 공백·탭 → 한 칸, 줄바꿈 정리)만이다. 현대 엔진(edge, OpenAI, Google)은 숫자·날짜를 대부분 스스로 읽으므로, 과한 정규화는 오히려 품질을 떨어뜨린다. 아래 규칙은 이름으로 켠다 (`normalizer_rules: [strip_urls, units]`).

| 규칙 이름 | 동작 | 예 |
|---|---|---|
| `strip_urls` | URL → "링크" 또는 제거 | `https://a.com` → `링크` |
| `strip_emoji` | 이모지 제거 | `좋아요 👍` → `좋아요` |
| `units` | 단위 기호 → 한국어 | `3kg` → `3킬로그램`, `25℃` → `25도` |
| `symbols` | 기호 → 읽는 말 | `A&B` → `A 앤 B`, `%` → `퍼센트` |
| `markdown` | 마크다운 문법 제거 | `**굵게**` → `굵게`, `# 제목` → `제목` |

숫자를 한글 수사로 바꾸는 규칙은 넣지 않는다. 한자어/고유어 수사 선택(`3개`=세 개, `3층`=삼 층)이 문맥에 따라 달라서 규칙으로 틀리기 쉽고, 엔진이 더 잘한다.

규칙은 순수 함수(`str -> str`)로 만들고 딕셔너리에 이름으로 등록한다. 적용 순서는 `markdown → strip_urls → strip_emoji → symbols → units → 공백 정리`로 고정한다 — URL 안의 기호가 `symbols`에 먼저 먹히면 안 되기 때문이다.

## 테스트해야 할 경계 사례

test-engineer에게 넘길 때 최소 이 목록은 포함되도록 한다.

- 빈 문자열, 공백·줄바꿈만 있는 입력 → 빈 리스트
- 종결 부호 없는 한 문장이 `max_chars`보다 김 → 공백 경계로 분할
- 공백 없는 `max_chars + 1`자 → `TextTooLongError`
- `3.14`, `Mr. Kim`, `1. 첫째` → 잘못 자르지 않음
- `그가 말했다. "정말?" 그리고 떠났다.` → 따옴표 포함 경계
- 이모지·결합 문자(자모 분리형 한글) 포함 → 글자 수 계산과 손실 없음
- 속성 기반 검사: 임의 텍스트에 대해 `all(1 <= len(c) <= max_chars)`, 공백 제거 후 연결 결과 = 원문 공백 제거 결과
